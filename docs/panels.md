# Panels

The dashboard **celestia-mon: Celestia validator**, in the **Celestia validator** folder, has up to 19 panels: a strip of six at the top (four without Fibre) that answers "is everything fine right now", then the groups Validator and signer, Fibre and Hosts. The install on the monitor builds it from your inventory: the signer panels appear only with `celestia_mon_signer: remote` (the group is then called Validator and signer, otherwise Validator), the Fibre group and the Fibre storage budget and Fibre endpoint tiles only with `celestia_mon_fibre_enabled: true`, and Blocks behind the highest node only with a backup node. With a local signer, Fibre off and one node, the dashboard has 11 panels. Dashed red lines sit at the alert thresholds in [alerts.md](alerts.md). With more than one host, each host keeps one colour across the panels. The validator role can move to a backup node and the Fibre role to a standby Fibre host, so no panel takes a role's host from the inventory: the signing node is the one the validator's signatures go through, and the active Fibre is the host whose Fibre unit systemd reports active. Services per host shows the role each server holds now.

Every graph carries a marker each time systemd starts celestia-appd, Fibre or tmkms: "<unit> started on <host>". A stop adds no marker. Markers can be missed on ranges longer than about a week, where Grafana takes coarser steps.

## Now

- **Node progress**: Is the node advancing, and is it peered? With one node, three tiles: new blocks committed locally in the last 3 minutes (red at 0; NodeNotAdvancing pages when no new block arrives for 3 minutes), block sync (orange "yes" while the node catches up) and peers (red at 0). With backup nodes, a table with one row per node (the validator node and each backup node): Blocks, the new blocks it committed in the last 3 minutes (red at 0, "down" while Prometheus cannot read its metrics); Lag, the blocks it trails the highest node of the install (orange above `node_behind_blocks`, 20 by default, where NodeBehind sends a message after 10 minutes; a backup node must stay near 0 to take over signing, and a node in block sync also lags; history in Blocks behind the highest node); and Peers (red at 0). NodeNotAdvancing pages when no node commits a block for 3 minutes. The panel shows that the nodes advance, not that they are at the network's head: compare the height with an explorer or [status.celestia.org](https://status.celestia.org/). If the whole chain stopped, coordinate with the other validators instead of fixing locally.
- **Signing**: Is my validator in the active set and signing right now, and through which node? Up to three tiles. Blocks since my last signature is counted across all nodes as ValidatorNotSigning does, so it follows the signer after a tmkms repoint: green while it signs, red above ValidatorNotSigning's threshold (10 blocks by default). The value is capped at 10 times the threshold and then reads "100+" (with the default threshold); right after a node start it sits there until the first own signature. The history is in Blocks since my last signature. The active set tile reads green "in active set, voting power" with the validator's voting power while a node records each block for the validator's key, as a signature or as a miss, and red "not in active set" while the chain moves and no node does: the validator is jailed, unbonded or outside the active set. celestia-core reports the voting power only while the key is in the set and keeps the last value after it leaves, so the tile tells the two apart by the signatures and misses, not by the power. It is left out while no node knows the validator's key (the node the signer uses is down, or it started while the validator was out of the set) and while the chain stands still. Signing on names the server the validator signs through now. With a remote signer, that is the node whose privval client made a signature in the last 2 minutes; a node that tmkms left keeps reading the validator's signatures from the chain, so only these count. It reads red "no signer connected" while the validator is in the active set and no node made a signature for 2 minutes; out of the active set a node asks for no signatures, so the tile is then left out. With a local key, it is the node whose last signed height advanced in the last 2 minutes.
- **Services per host**: Which role does each server hold now, are celestia-appd, Fibre and tmkms running, and how often did systemd restart them? First one role tile per server ("<host> role"), read from the metrics, so it follows a tmkms repoint or a Fibre failover: "Validator (signing)" for the node the signer signs through (as Signing on), "Backup node" for every other node while one signs, and red "Node (not signing)" for every node while none signs; with Fibre on, "Fibre (active)" for the host whose Fibre unit is active and grey "Fibre (standby)" for every other Fibre host. A server with a node and a Fibre names both, for example "Backup node, Fibre (active)". The KMS and monitor hosts have no role tile. Then one tile per unit: green "active" or red "not active", and restarts in the last 24 hours (orange from 1). A stopped Fibre unit reads grey "standby" while another host's Fibre unit is active, and red "none active" when no Fibre unit is active anywhere (FibreDown pages after 10 minutes). A Fibre host whose node_exporter lists no Fibre unit reads the same way: systemd unloads a stopped, disabled standby. Only automatic restarts under `Restart=` count; a manual stop and start does not. A red "not reporting" tile appears while Prometheus cannot read a host's metrics (celestia-app, node_exporter or the Fibre collector): that host's other tiles are then missing, not fine.
- **Link load (busiest minute, last hour)**: Is any host's link close to full, in either direction? One bar per host and direction: the busiest 1-minute average in the last hour, against `celestia_mon_link_mbps` or, when that is not set, the NIC port speed. Orange from 70%, because 1-minute averages hide sub-second bursts, and red from 90%. Every physical NIC counts; VPN, container, bridge, bond master and VLAN interfaces are left out. "speed unknown: set celestia_mon_link_mbps" means the NIC reports no speed (common on VMs): set `celestia_mon_link_mbps` for that host. Port speed can be above what your provider lets through, so set it too when your plan is below the port speed. A full link shows up as upload timeouts and late votes; the fix is a bigger plan or port, or moving Fibre to its own host. Current load over time: Network traffic.
- **Fibre storage budget used**: Which host runs the active Fibre, and how full is its storage budget? The tile shows only the host whose Fibre unit is active, named "Active Fibre: <host>", and follows it when a standby Fibre takes over. It has no value while no Fibre unit is active, or while the active Fibre sends no metrics. The reading is the share of this server's stake-based storage budget held by shards, on disk plus in-flight reservations; at 100% the storage limiter rejects uploads (`budget_exceeded`). A sparkline shows it over the dashboard range; orange from 90%. Shards are kept for the shard-retention window (4 h by default). The budget is the full-stake limit (2 TiB per window by default, about 146 MiB/s) times this validator's share of rows, and every blob gives the validator that same share, so the reading follows the network's Fibre data in the window: rejections near 100% come from network load, not a local fault. Each blob also adds proofs and a 64 KiB RLC, about 2.2 MB at full stake and 3.9 MB at the 148-row minimum, so small blobs read high (a 1 MiB blob counts as 3-5 MB) and low-stake validators reach the limit first. "No limit" means the budget is unlimited, or the validator was not in the active set when Fibre started. The reading falls to 0 while the validator is out of the active set.
- **Fibre endpoint**: Is the Fibre endpoint registered on chain reachable from outside, and is it the active Fibre server's? The check comes from [Tensile](https://tensile.huginn.tech), which dials every validator's registered Fibre endpoint from outside; celestia-mon-tensile on the monitor reads it every minute (`celestia_mon_tensile` in the inventory). The first tile names the registered `host:port`: green "reachable from outside" or red "unreachable" at Tensile's last check, and grey "not checked yet" until Tensile has checked a new registration. TLS identity, for an endpoint Tensile reached: green "verified" when the endpoint's TLS identity is endorsed by the validator's consensus key, red "not verified" when it is not. A red "wrong endpoint" tile, named "points to <endpoint>, Fibre runs on <host>", appears while the registration does not name the `celestia_mon_fibre_public_endpoint` of the host whose Fibre unit is active; it needs that endpoint in the inventory and exactly one active Fibre. "registered endpoint" reads red "none" while nothing is registered. "since last outside check" shows how long ago Tensile last checked the endpoint. FibreDown pages when the registered endpoint stays unreachable, names another host than the active Fibre, or nothing is registered, for 10 minutes. Without `celestia_mon_tensile` the tile reads grey "not checked (Tensile not configured)", and red "celestia-mon-tensile not reporting" while Prometheus cannot read the service.

## Validator and signer

The group's first line is about the validator's signatures and nodes: Blocks since my last signature; Missed blocks, last hour; and, with backup nodes, Blocks behind the highest node. With a remote signer, Signer latency vs 10 ms and Signing failures by reason follow on a second line.

- **Blocks since my last signature**: Is my validator signing right now? One line, counted across all nodes as ValidatorNotSigning does, so it goes on when the signer moves to a backup node. Near 0 while it signs; a line that climbs means blocks pass without its signature, and the dashed line is where ValidatorNotSigning fires. It works after restarts and jails, when missed-block counters freeze. The line stops at 10 times the ValidatorNotSigning threshold (100 blocks by default): right after a node start the value is the full block height until the first own signature, and one restart would otherwise flatten the chart. The alert uses the uncapped value.
- **Missed blocks, last hour**: Does my validator miss signatures now and then? One line per node: the share of the blocks it committed in the last hour that carry no signature from the validator, as SignaturesMissed computes it. The dashed line is `signatures_missed_ratio` (5% by default), where SignaturesMissed sends a message after 10 minutes. Each node that knows the validator's key reads the signatures from the chain's commits, so a node that tmkms left keeps counting and the alert takes the highest line; a node without the key has no line. A node reads 0 until its first miss since it started. Signatures that time out now and then, from load on the KMS host or loss on the link to it, show here while Blocks since my last signature stays low. The share says how often signatures are missed, not how close the validator is to being jailed.
- **Blocks behind the highest node** (with backup nodes only): Is every node keeping up with the others? One line per node: the blocks it trails the highest node of this install. A backup node must stay near 0 to take over signing; a node in block sync also lags. The dashed line is `node_behind_blocks` (20 by default), where NodeBehind sends a message after 10 minutes. NodeBehind also fires for a node that stops while another advances; Node progress shows that as 0 new blocks. The current lag is the Lag column of Node progress.
- **Signer latency vs 10 ms**: Am I within Celestia's 10 ms median requirement, and is consensus or Fibre (`raw_bytes`) signing getting slower? The median of the last 50 signatures must stay under the dashed 10 ms line; the p99 lines per message type show which kind of signature slows down. The median appears after 50 signatures since the node started and stays frozen while none succeed.
- **Signing failures by reason**: Which signing path fails? Empty on a healthy setup. `no_connection` or `timeout`: the KMS host or the link; proposal only: the KMS cannot propose; `raw_bytes` only: tmkms too old for Fibre. Every retry counts as a failure, so a short outage shows as a burst. The panel shows the failures in each 5-minute window. A failure counter appears with its first failure, so the first failure of each kind after a node start does not show.

## Fibre

The panels show each Fibre host's series under its host name. Only the active Fibre sends Fibre metrics, so they follow the active host after a failover; the Fibre disk panel shows the Fibre mount of every Fibre host, the standby's too. Panel links open the official [Fibre](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/observability/docker/grafana/dashboards/fibre.json) and [Fibre runtime](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/observability/docker/grafana/dashboards/fibre-runtime.json) dashboards for per-RPC and Go runtime detail, and [Tensile](https://tensile.huginn.tech) for the view from outside.

- **Time since last accepted upload**: Is Fibre serving, not just running? A sawtooth that drops back with each accepted upload is healthy; a line that climbs past the dashed threshold (ten uploads at this server's 7-day average rate, never under 1 hour, drawn as its own "alert threshold" series) is FibreNotServing. Until the first accepted upload after a start, a separate series, "no accepted upload yet (since Fibre start)", counts from Fibre's start. There is no threshold line when the server had no upload in 7 days. A quiet network also makes the time grow. To tell a quiet network from a fault, check on [Tensile](https://tensile.huginn.tech) whether the network is carrying Fibre uploads.
- **Shard requests**: Are uploads and downloads arriving and succeeding, is the storage limiter refusing uploads, and are uploads slow? Requests per second by `success`; rejected uploads by reason (the storage limiter refusing uploads); upload p95 latency on the right axis.
- **Fibre disk**: Will the Fibre disk hold the stake-based storage budget? Occupancy near the budget is normal at full load; worry when the free space is smaller than the budget minus occupancy (DiskLow). A budget of 0 means no limit: Fibre found no stake for the validator.

## Hosts

Panel links open [Node Exporter Full](https://grafana.com/grafana/dashboards/1860-node-exporter-full/) for everything else about a host. The group has two lines: Network traffic and CPU per host, then Disk latency and load, Free space per data disk and Memory per host.

- **Network traffic**: What is using each host's link over time, and how much of it is Fibre? Traffic of the whole machine, not just Celestia: receive above zero, transmit below, as 5-minute averages (the Link load tile has the 1-minute peaks). With Fibre on, dashed lines show the Fibre shards accepted and served: shard row data that was signed, including re-uploads of a shard already held, without proofs, RLC or rejected uploads. They are drawn over the NIC line, not subtracted from it; the gap covers consensus P2P, RPC, row proofs and RLC, TLS, and rejected uploads. If Fibre fills the link, size the link up or move Fibre to its own host; if something else does, look for snapshot or state-sync serving, or RPC load.
- **CPU per host**: Is a host short of CPU? The share of all cores busy, as a 5-minute average; on a VM, steal counts as busy. A validator host near 100% votes late and adds to signer latency; a Fibre host near 100% slows uploads: size the host up or move Fibre off it. The KMS host appears only with `celestia_mon_kms_scrape: true`. One pegged core may not show: see Node Exporter Full.
- **Disk latency and load**: Is each disk answering in time? The average time one read or write took, per physical disk, with the bytes moved as dashed lines on the right axis. High latency with high load: something on the host loads the disk (Fibre, compaction, Prometheus); give Fibre its own disk. High latency with low load: the disk or the provider's storage is slow. LVM, RAID, ZFS volume and CD devices are left out; their physical disks count, and `lsblk` maps mounts to devices. Where the monitor shares a disk with the validator or Fibre, `celestia-mon-doctor` check 16 compares this around Prometheus's compactions ([quickstart step 9](quickstart.md#9-run-doctor)).
- **Free space per data disk**: Which data disk is close to full or read-only? One bar per configured mount: red below 5% free, orange below 10%, green above (the DiskLow thresholds); the read-only tile turns red on "yes".
- **Memory per host**: Is Fibre or the node running out of RAM? Available memory per host; OOM kills in the last hour on the right axis. Fibre can use up to about 27 GiB at its default connection limits ([connection caps and memory](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/fibre/cmd/README.md#connection-caps-and-memory)); any OOM kill means the kernel killed a process, and `journalctl -k` names it.
