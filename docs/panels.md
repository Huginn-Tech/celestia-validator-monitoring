# Panels

The dashboard **celestia-mon: Celestia validator**, in the **Celestia validator** folder, has up to 16 panels: a strip of five at the top (four without Fibre) that answers "is everything fine right now", then the groups Validator and signer, Fibre and Hosts. The install on the monitor builds it from your inventory: the signer panels appear only with `celestia_mon_signer: remote` (the group is then called Validator and signer, otherwise Validator), and the Fibre group and the Fibre storage budget tile only with `celestia_mon_fibre_enabled: true`. With a local signer and Fibre off, the dashboard has 10 panels. Dashed red lines sit at the alert thresholds in [alerts.md](alerts.md). With more than one host, each host keeps one colour across the panels.

Every graph carries a marker each time systemd starts celestia-appd, Fibre or tmkms: "<unit> started on <host>". A stop adds no marker. Markers can be missed on ranges longer than about a week, where Grafana takes coarser steps.

## Now

- **Node progress**: Is the node advancing, and is it peered? Three tiles: new blocks committed locally in the last 3 minutes (red at 0; NodeNotAdvancing pages when no new block arrives for 3 minutes), block sync (orange "yes" while the node catches up) and peers (red at 0). It shows that the node is advancing, not that it is at the network's head: compare its height with an explorer or [status.celestia.org](https://status.celestia.org/). If the whole chain stopped, coordinate with the other validators instead of fixing locally.
- **Signing**: Is my validator signing right now? Blocks since my last signature: green while it signs, red above ValidatorNotSigning's threshold (10 blocks by default). The value is capped at 10 times the threshold and then reads "100+" (with the default threshold); right after a node start it sits there until the first own signature. The history is in Blocks since my last signature.
- **Services per host**: Are celestia-appd, Fibre and tmkms running, and how often did systemd restart them? One tile per unit: green "active" or red "not active", and restarts in the last 24 hours (orange from 1). Only automatic restarts under `Restart=` count; a manual stop and start does not. A red "not reporting" tile appears while Prometheus cannot read a host's metrics (celestia-app, node_exporter or the Fibre collector): that host's other tiles are then missing, not fine.
- **Link load (busiest minute, last hour)**: Is any host's link close to full, in either direction? One bar per host and direction: the busiest 1-minute average in the last hour, against `celestia_mon_link_mbps` or, when that is not set, the NIC port speed. Orange from 70%, because 1-minute averages hide sub-second bursts, and red from 90%. Every physical NIC counts; VPN, container, bridge, bond master and VLAN interfaces are left out. "speed unknown: set celestia_mon_link_mbps" means the NIC reports no speed (common on VMs): set `celestia_mon_link_mbps` for that host. Port speed can be above what your provider lets through, so set it too when your plan is below the port speed. A full link shows up as upload timeouts and late votes; the fix is a bigger plan or port, or moving Fibre to its own host. Current load over time: Network traffic.
- **Fibre storage budget used**: Share of this server's stake-based storage budget held by shards, on disk plus in-flight reservations; at 100% the storage limiter rejects uploads (`budget_exceeded`). A sparkline shows it over the dashboard range; orange from 90%. Shards are kept for the shard-retention window (4 h by default). The budget is the full-stake limit (2 TiB per window by default, about 146 MiB/s) times this validator's share of rows, and every blob gives the validator that same share, so the reading follows the network's Fibre data in the window: rejections near 100% come from network load, not a local fault. Each blob also adds proofs and a 64 KiB RLC, about 2.2 MB at full stake and 3.9 MB at the 148-row minimum, so small blobs read high (a 1 MiB blob counts as 3-5 MB) and low-stake validators reach the limit first. "No limit" means the budget is unlimited, or the validator was not in the active set when Fibre started. The reading falls to 0 while the validator is out of the active set.

## Validator and signer

- **Blocks since my last signature**: Is my validator signing right now? Near 0 while it signs; a line that climbs means blocks pass without its signature, and the dashed line is where ValidatorNotSigning fires. It works after restarts and jails, when missed-block counters freeze. The line stops at 10 times the ValidatorNotSigning threshold (100 blocks by default): right after a node start the value is the full block height until the first own signature, and one restart would otherwise flatten the chart. The alert uses the uncapped value.
- **Signer latency vs 10 ms**: Am I within Celestia's 10 ms median requirement, and is consensus or Fibre (`raw_bytes`) signing getting slower? The median of the last 50 signatures must stay under the dashed 10 ms line; the p99 lines per message type show which kind of signature slows down. The median appears after 50 signatures since the node started and stays frozen while none succeed.
- **Signing failures by reason**: Which signing path fails? Empty on a healthy setup. `no_connection` or `timeout`: the KMS host or the link; proposal only: the KMS cannot propose; `raw_bytes` only: tmkms too old for Fibre. Every retry counts as a failure, so a short outage shows as a burst. The panel shows the failures in each 5-minute window. A failure counter appears with its first failure, so the first failure of each kind after a node start does not show.

## Fibre

Panel links open the official [Fibre](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/observability/docker/grafana/dashboards/fibre.json) and [Fibre runtime](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/observability/docker/grafana/dashboards/fibre-runtime.json) dashboards for per-RPC and Go runtime detail, and [Tensile](https://tensile.huginn.tech) for the view from outside.

- **Time since last accepted upload**: Is Fibre serving, not just running? A sawtooth that drops back with each accepted upload is healthy; a line that climbs past the dashed threshold (ten uploads at this server's 7-day average rate, never under 1 hour, drawn as its own "alert threshold" series) is FibreNotServing. Until the first accepted upload after a start, a separate series, "no accepted upload yet (since Fibre start)", counts from Fibre's start. There is no threshold line when the server had no upload in 7 days. A quiet network also makes the time grow. To tell a quiet network from a fault, check on [Tensile](https://tensile.huginn.tech) whether the network is carrying Fibre uploads.
- **Shard requests**: Are uploads and downloads arriving and succeeding, is the storage limiter refusing uploads, and are uploads slow? Requests per second by `success`; rejected uploads by reason (the storage limiter refusing uploads); upload p95 latency on the right axis.
- **Fibre disk**: Will the Fibre disk hold the stake-based storage budget? Occupancy near the budget is normal at full load; worry when the free space is smaller than the budget minus occupancy (DiskLow). A budget of 0 means no limit: Fibre found no stake for the validator.

## Hosts

Panel links open [Node Exporter Full](https://grafana.com/grafana/dashboards/1860-node-exporter-full/) for everything else about a host. The group has two lines: Network traffic and CPU per host, then Disk latency and load, Free space per data disk and Memory per host.

- **Network traffic**: What is using each host's link over time, and how much of it is Fibre? Traffic of the whole machine, not just Celestia: receive above zero, transmit below, as 5-minute averages (the Link load tile has the 1-minute peaks). With Fibre on, dashed lines show the Fibre shards accepted and served: shard row data that was signed, including re-uploads of a shard already held, without proofs, RLC or rejected uploads. They are drawn over the NIC line, not subtracted from it; the gap covers consensus P2P, RPC, row proofs and RLC, TLS, and rejected uploads. If Fibre fills the link, size the link up or move Fibre to its own host; if something else does, look for snapshot or state-sync serving, or RPC load.
- **CPU per host**: Is a host short of CPU? The share of all cores busy, as a 5-minute average; on a VM, steal counts as busy. A validator host near 100% votes late and adds to signer latency; a Fibre host near 100% slows uploads: size the host up or move Fibre off it. The KMS host appears only with `celestia_mon_kms_scrape: true`. One pegged core may not show: see Node Exporter Full.
- **Disk latency and load**: Is each disk answering in time? The average time one read or write took, per physical disk, with the bytes moved as dashed lines on the right axis. High latency with high load: something on the host loads the disk (Fibre, compaction, Prometheus); give Fibre its own disk. High latency with low load: the disk or the provider's storage is slow. LVM, RAID, ZFS volume and CD devices are left out; their physical disks count, and `lsblk` maps mounts to devices. Where the monitor shares a disk with the validator or Fibre, `celestia-mon-doctor` check 16 compares this around Prometheus's compactions ([quickstart step 9](quickstart.md#9-run-doctor)).
- **Free space per data disk**: Which data disk is close to full or read-only? One bar per configured mount: red below 5% free, orange below 10%, green above (the DiskLow thresholds); the read-only tile turns red on "yes".
- **Memory per host**: Is Fibre or the node running out of RAM? Available memory per host; OOM kills in the last hour on the right axis. Fibre can use up to about 27 GiB at its default connection limits ([connection caps and memory](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/fibre/cmd/README.md#connection-caps-and-memory)); any OOM kill means the kernel killed a process, and `journalctl -k` names it.
