# Panels

The dashboard **Celestia validator**, in the **Celestia validator** folder, reads like a status page for one validator setup. The first screen answers, top to bottom: whose validator and which network, is anything wrong, is each part fine, was it fine over the last day, which server held each role, and how each server is doing now. Right under it, the closed row **All firing alerts** lists every alert in full; then the rows **Validator** and **Fibre** (open) hold the charts that explain those answers, **Servers** (open) has a column of hardware charts for each server, and **Servers: disks, restarts and clocks** and **Network upgrade** (closed) hold the detail. The install on the monitor builds the dashboard from your inventory: panels that do not apply are left out (no signer panels with a local key, no Fibre panels with Fibre off, no backup panels with one node, no outside check without `celestia_mon_tensile`, no upgrade panels without `celestia_mon_signal`). The default range is 24 hours, refreshed every 30 seconds; times are in UTC.

**Colours mean state, and only where an alert watches.** Every word, bar and cell follows one rule, printed in the key line under the role band ("Fine · Warning · Urgent · No data"), which on a wide enough screen first names each server in its colour:

- **Fine**: green on the Status cell and the answers, plain text elsewhere, or a muted green bar.
- **Warning** (amber): the problem an alert watches is true, the alert is pending, or a message alert fires. If it lasts, you get the alert.
- **Urgent** (red): a page alert fires.
- **No data** (grey).

Amber and red appear only where an alert rule in [alerts.md](alerts.md) watches the condition, at the rule's own threshold, so anything amber reaches you if it lasts. Facts no alert watches (CPU, memory, link load, the storage budget, proposals, uptime shares) are drawn in neutral colours whatever their value. The one exception is "Fibre signs through" (below), amber while Fibre's last signatures went through another node than the validator's: no rule backs it, because after a tmkms repoint on a network that sends no blob, Fibre's last signatures stay on the old node for up to an hour even when Fibre already dials the right one. When blobs come and Fibre still dials the old node, FibreNotServing ("Uploads failing") sends a message. The Status cell, the answers, the cards and the History bars read Prometheus's own alert states, so they always agree with the alerts you received. Silences stop notifications only: a silenced alert still shows here.

**Servers and roles.** A server is every host node_exporter runs on: the validator node and the backup nodes first, then the Fibre hosts, then KMS hosts with `celestia_mon_kms_scrape: true`, then the monitor where it has a host of its own, in inventory order. Each server keeps one colour (blue, light purple, cyan, light blue) in every line, fill, bar and sparkline it owns and in its name; what belongs to the whole network is drawn in the text colour, and amber and red appear only where an alert's condition holds. Roles move between hosts (a tmkms repoint to a backup node, a Fibre failover), so no panel takes a role from the inventory: the signing node is the node the validator's signatures go through, and the active Fibre is the host whose Fibre unit systemd reports active.

## First screen

### Top strip

One framed band of six cells of equal width, each a small label over a larger value, set from the left, so the labels share one line and the values another; the answers below are cells of the same style on the same column edges. The strip, the answers and the six-cell rows of the Validator, Fibre and Network upgrade sections share one value size, so their proportions match: the largest of 22, 20 and 18 px at which every word and number of every one of those cells fits on one line on a 1440-pixel screen with the menu docked, measured letter by letter in Grafana's font (with the outside check's words, such as "Rows not served", that is 18 px). A fact that cannot be read says "No data".

- **Name and network**: `celestia_mon_validator_name` (or "Validator") under the network, read from the nodes' own metrics (`chain_id`): "Celestia mainnet" or "Mocha testnet". A Mocha and a mainnet dashboard cannot be confused. A long name makes the values of every six-cell row smaller; the install stops on a name of more than 17 characters. "No node data" while no node answers.
- **Status**: green "All online", or what is wrong right now, or about to be, in a few words: the worst item, urgent before warning. Red: a page alert fires. Amber: a message alert fires, or an alert's problem is true and it will be sent if it lasts. The label line names the part the worst item is about and, with several items, counts them: "Status · Fibre" over "Not running", "Fibre · 3 alerts"; the value is the same word the answers, cards and History use for that state. An announcement shows in the text colour. The row **All firing alerts**, right under History, lists every alert in a plain sentence, with its rule name as your notification's first line carries it, its server and how long it has been active. Follow-on alerts are grouped into their cause, as Alertmanager's inhibitions do (no "Missed blocks" while "Not signing" shows; a server whose node_exporter does not answer counts once, as "Not reporting"). A scheduled network upgrade is no fault and does not show here: the Network upgrade answer (Governance with the vote check) shows it, and so does a vote still open before GovVoteMissing's limits. "All online" needs nothing wrong, the alert rules to have run in the last 2 minutes and Alertmanager to be up and reached.
- **Latest block**: the newest block any node of this setup committed. It grows by about 20 a minute; compare it with an explorer or [status.celestia.org](https://status.celestia.org/).
- **Block time**: the average time between blocks over 5 minutes, from the blocks' own timestamps. About 2.9 s is normal today; slower blocks affect every validator. Amber "Stalled" when no block arrived in those 5 minutes.
- **Voting power**: this validator's share of the active set's voting power. "Out of set" while the chain moves but no node records blocks for the validator's key (jailed, unbonded, outside the set); "Stalled" while no block arrives, when the share cannot be read.
- **Blocks signed, 30 d**: the share of the blocks committed over the last 30 days (or the retention, if shorter) that carry the validator's signature. Blocks while it was not signing at all count as unsigned, and so does the jump of a node that catches up after an outage; time without monitoring is left out. Explorers count over the chain's slashing window, so their number can differ.

The Status words and what they stand for (hover the cell's (i) for the list of your install):

| Status | Alert or condition |

### Answers

A label over one word each, in cells of the top strip's style on its column edges: green while fine, amber while the problem an alert watches is true or its alert is pending, red once its page fires. Words that only inform ("Signal sent", "Vote open", "Upgrade set", "Switching", "Two nodes") are plain text, and Signing through names the server in its colour. Hover the (i) for every word.

- **Validator**: "Signing" while its signature is on one of the last 10 blocks (`not_signing_blocks`). "Missed blocks" (SignaturesMissed's condition), "Not signing" (ValidatorNotSigning's), "Out of set", "Nodes stalled" (no node committed a block for 2 minutes: NodeNotAdvancing's), "Nodes offline", and "Not seen": no signature while a node Prometheus cannot read may still be signing. Check an explorer before you move the key anywhere: two signers of one key double-sign.
- **Signing through**: the server whose node the validator signs through now; with a remote signer, the node whose privval client signed a vote or proposal in the last 2 minutes (a node that tmkms left keeps reading the validator's signatures from the chain, so only signatures made through the node count). "Switching" for up to 2 minutes after a tmkms repoint, while both nodes have recent signatures. "Two signers" while two nodes keep getting the validator's signatures: amber while ValidatorSigningTwice is pending, red once it pages, about 3 minutes after the second signer started; one key signing through two nodes can double-sign. If tmkms is set up to sign through several nodes on purpose, set `celestia_mon_signer_multi_node: true` and it reads "Two nodes" in plain text. "Not signing" while the validator is asked to sign and no node does (check tmkms and the link to it; red once ValidatorNotSigning pages); "Not visible" while a node that may still sign is not reporting.
- **Servers** (only where the answers would be four or five, so they make six and line up with the strip): the server lines of History now, the worst first, in their colours. "All up" while every server's node_exporter answers, no server alert fires and the alert rules ran; red "Disk critical" while DiskLow pages; "Not reached" while the monitor reaches none of a server's metrics endpoints (MonitorCannotReach: amber for one server, red once it reaches no server and pages); amber in ServiceDown's words, as the Status cell has them ("Not reporting", "No node data", "Node stopped", "Node crashing", "Node missing", and the signer's and Fibre's); red "No peers" while NodePeersLow pages (the node the validator signs through has none); amber "Disk low", "Few peers" (NodePeersLow's message: a node with fewer than 2 peers), "Node behind", "RAID degraded" (RaidDegraded), "No time sync" (ClockNotSynced), or "Warning" for another warning that names a server; grey "No data". Which server: its column in the Servers band and its line in History. Whether a backup node could take over signing: its card in the Servers band ("Backup, in sync · 28 peers", amber "Node behind · 35 blocks").
- **Fibre** (Fibre on): "Serving" while one Fibre server runs and no Fibre alert holds. No recent upload is needed: on a quiet network no blob may come for hours, and that is normal. Amber while FibreNotServing is pending or fires, by its reason: "Uploads missed" and "Rows not served" (with `celestia_mon_tensile`), "Uploads failing" (most often Fibre still signs through a node that tmkms left), "Not ready" (Fibre's own health check fails; red once it pages, after 10 minutes), "No Fibre data" (no Fibre metrics). "Two Fibres" (FibreBothActive), "Not running" (no Fibre unit active anywhere: amber during a failover, red once FibreDown pages), "Not seen" (a Fibre host's node_exporter does not answer, so its unit state is unknown), and, with the outside check, "Unreachable", "Wrong host" and "Not registered" as in Fibre from outside (red once FibreDown pages). Which server runs it: the Servers band.
- **Fibre from outside** (with `celestia_mon_tensile`): [Tensile](https://tensile.huginn.tech)'s check of the Fibre endpoint registered on chain, from outside your network, read every minute. "Reachable"; "Unreachable", "Wrong host" (the chain names another endpoint than the active Fibre host's `celestia_mon_fibre_public_endpoint`; after a failover, send `set-host`) and "Not registered", amber, then red when FibreDown pages; grey "Not checked" while no check is under 15 minutes old, grey "Check pending" until Tensile has checked a new registration, amber "Check stopped" once TensileUnreadable fires.
- **Network upgrade** (with `celestia_mon_signal`), titled **Governance** while it also reads the votes (unless `celestia_mon_signal` sets `gov: false`): "None pending" almost always. "Signal sent" while a signalling round is open and the validator signalled; "Not signalled" while it has not (red once UpgradeSignalMissing pages); "Upgrade set" once the upgrade height is set (UpgradeScheduled); amber "Upgrade soon" within 24 hours of it (UpgradeSoon); grey "Not checked" while no read of the chain (or, as Governance, of the proposals) is under 15 minutes old, amber "Signal stale" once SignalUnreadable fires. As Governance also "Vote open" in plain text while a proposal is in its voting period and the validator account has not voted on it, before GovVoteMissing's limits; amber "Vote missing" while GovVoteMissing is pending or fires (less than 2 days of the vote left, or less than half of a shorter one), red once it pages (less than a day left, with `gov_page`). The worst shows first: red "Not signalled", red "Vote missing", "Upgrade soon", amber "Vote missing", "Signal stale", "Not checked", "Upgrade set", amber "Not signalled", "Vote open", "Signal sent". The dashboard cannot see silences: a round opened before any release exists stays red while you silence its page ([alerts.md](alerts.md#upgradesignalmissing)).
- **Monitoring** (only where the answers would be four, as the sixth): "Working" while the alert rules ran in the last 2 minutes and none failed, Alertmanager is up and reached and the heartbeat goes to your dead-man service. Amber "Rules stopped", "Rules failing" (MonitoringBroken), "Alerting down" (Alertmanager does not answer), "Alerts unsent" (NotificationsFailing, or alerts that did not reach Alertmanager), "No heartbeat" (DeadmanFailing) and, with `celestia_mon_announcements`, "Feed stopped" (AnnouncementsUnreadable). Its past: the monitor's server line in History.

### Servers

What runs where now, one column per server in the order above, and one more for a remote signer whose host is not scraped. The columns share the width evenly: two halves, three thirds or four quarters (with shorter row names); one server's card and its Hardware now sit side by side. With five servers or more, a table takes the band's place (below).

Each column is a card titled with the server's name, over its **Hardware now**. Each card lists only the parts that run on that server, always in the order Consensus node, Fibre, Monitoring; a card with fewer parts ends in blank lines, so every card keeps one height and one row spacing (a server that runs none of them, such as a Fibre host while `celestia_mon_fibre_enabled` is false, has an empty card over its Hardware now). Roles are read from the metrics, so a tmkms repoint or a Fibre failover moves the words between cards.

- **Consensus node**: "Signing · 50 peers" while the validator's signatures go through this node; "Backup, in sync · 28 peers" for a node within 20 blocks (`node_behind_blocks`) of the highest node, which can take over; "Syncing, 1200 behind" during block sync; "In sync · 30 peers" while nobody is asked to sign (out of set). The peers are the node's connected peers. Amber "Few peers · 1" while the node has fewer than 2 (`peers_message_below`, NodePeersLow pending or firing); red "No peers" once NodePeersLow pages for the node the validator signs through. Amber "Node behind · 35 blocks" (NodeBehind's condition), "Stalled" (its height has not moved for 2 minutes), "No node data" (celestia-appd's metrics are gone), "Not reporting" (the server's node_exporter does not answer), "Node crashing" (ServiceDown's crash loop) and "Not signing" while no node signs (red once ValidatorNotSigning pages). "Two signers" on each node that keeps getting the validator's signatures while another does too: amber while ValidatorSigningTwice is pending, red once it pages (not with `celestia_mon_signer_multi_node`).
- **Fibre** (Fibre on): "Active, serving" where the Fibre unit runs and no Fibre alert holds; "Standby, stopped" where it is installed and stopped on purpose, which is fine. Amber, on the host whose Fibre runs, while FibreNotServing is pending or fires: "Uploads missed", "Rows not served", "Uploads failing", "Not ready" (red once it pages), "No Fibre data"; "Two Fibres" (FibreBothActive); "Not running" while no Fibre runs anywhere (red once FibreDown pages); "No Fibre data" where a standby's OpenTelemetry collector does not answer, so it could not report if started; "Not reporting"; "Fibre crash" (ServiceDown's crash loop).
- **Monitoring**: on the monitor's server, "Working", or the Monitoring answer's words.

A monitor on a host of its own (as `mon-1` in the mainnet example) is a server too, in its own colour: its Monitoring row and its Hardware now, whose Disk used is the disk of Prometheus's data (list it in `celestia_mon_data_mounts`).

The remote signer's card is titled "kms-server · remote signer" (the `kms` host's name; the name alone where the column is too narrow): **Validator signs through** (the server, in its colour; "Switching" during a repoint, "Two signers" as on the node rows), with Fibre on **Fibre signs through** (the node Fibre's own signatures go through, from the last hour, else the last day on a quiet network; amber while it is not the node the validator signs through: point Fibre's signer address at the signing node; grey "None in 24 h" while Fibre signed nothing in a day), and with `celestia_mon_kms_scrape` **Signer service** (tmkms's unit: "Running", amber "Signer down", "No signer" (not loaded), "Not reporting", "Signer crash", ServiceDown's words).

**Hardware now**: four bars in the server's colour, each named on its left (the names right-aligned in one column, so the bars start on one line; beside a remote signer's column that column is as wide as the signer's, so every bar of the band starts on one line), with its share in use after a faint track: **CPU** (5-minute average; on a VM, steal counts as busy), **Memory**, **Disk used** (the fullest disk DiskLow watches: the data disks you listed, and a Fibre store while Fibre reports no storage budget) and **Network peak** (the busiest minute of the last hour, in or out, against `celestia_mon_link_mbps`, else the NIC speed; grey "Speed unknown" while neither is known). No alert watches CPU, memory or the link, so their bars keep the server's colour. Disk used turns amber at 90% (below 10% free, `disk_message_free_ratio`) and red "Disk critical" once DiskLow pages (below 5% free or read-only, `disk_page_free_ratio`, on the data disks of node and KMS hosts), DiskLow's levels and the dashed lines of the Disk used chart in the closed Servers row. Where DiskLow only sends messages (a Fibre-only server, a monitor on a host of its own), the bar never turns red. It shows DiskLow's other conditions in DiskLow's words: amber "Disk low" while a watched disk is read-only and DiskLow sends a message for it, or a Fibre store has less free space than its storage budget still needs. Grey "Fibre store" on a server whose only watched disk is a Fibre store with a storage budget: its fill is normal, and the Fibre row shows it.

Under a signer that is not scraped, its signing time instead, in ms, read on the node the validator signs through: **Median (alert at 10 ms)**, the median of the last 50 signatures (amber from 10 ms, `signer_median_seconds`, RemoteSignerProblem); the slowest 1% of vote signatures over 5 minutes (**Slowest 1%, votes**); of block proposals over 24 hours (**Slowest 1%, proposals**, amber "Bad proposals" while RemoteSignerProblem's proposal condition holds); and with Fibre, of Fibre's signatures over the last hour (**Slowest 1%, Fibre**; without Fibre, **Slowest 1%, 24 h** of every signature). Grey "None" where no such signature was made in the window.

### History

One panel: one line per check, a gap, then one line per server, one bar per time block: 10 minutes on the default 24 hours (144 bars), 1 hour on 7 days, 6 hours on 30 days. The bars follow the time picker and line up with the charts below. The newest bar on the right is the current block and fills in as its minutes pass; in its first 30 seconds it shows the 2 minutes before it. A bar shows the worst moment of its block, read from the alert states Prometheus evaluated at the time, so each alert colours one line; NodeBehind colours Node in sync and the line of the server that lags, and MonitorCannotReach's page every server's line but the monitor's. The monitoring has no line of its own: its alerts colour the monitor's server line. Network upgrades and governance votes have no line: the Network upgrade answer (Governance) shows them. A bar is green only while the alert rules ran in its block; grey means no data: before the install, monitoring down, the rules not running, or nothing to check. Hover a bar to see every line at that moment. Each bar is drawn centred on the start of its block, half a block left of the charts below. History has no time axis: the key line under the role band prints the range's first and last moment, in UTC, under the two ends of the bars.

The **Uptime** column beside it prints each line's uptime over the selected range on the line itself. It counts the time an alert fired, not the time one was only pending, so a line can read 100% beside an amber bar. Every bar names its state with the alert's own words, as the Status cell does (hover a bar).

| Line | Shown | Amber | Red | Uptime % |
|---|---|---|---|---|
| Node in sync | always | NodeNotAdvancing pending ("Nodes stalled"), NodeBehind fired for any node ("Node behind") | NodeNotAdvancing fired | minutes in which the nodes advanced and none was behind |
| Validator signing | always | ValidatorNotSigning pending ("Not signing"), SignaturesMissed fired ("Missed blocks"), ValidatorSigningTwice pending ("Two signers") | ValidatorNotSigning fired, ValidatorSigningTwice fired | share of the blocks that carry the validator's signature, counted as in Blocks signed |
| Remote signer | remote signer | RemoteSignerProblem fired ("Signer slow", "Bad proposals"); "No signatures" in any minute of the block in which the chain recorded misses and no node signed; ValidatorSigningTwice pending | ValidatorSigningTwice fired | minutes in which it signed without a signer alert, among the minutes it was asked to sign |
| Fibre serving | Fibre on | FibreDown pending ("Not running"); FibreNotServing fired, by its reason ("Uploads missed", "Rows not served", "Uploads failing", "Not ready", "No Fibre data"); FibreBothActive ("Two Fibres") | FibreDown fired (no Fibre unit active); FibreNotServing paged ("Not ready") | minutes with a Fibre unit active and neither FibreNotServing nor FibreBothActive firing |
| Fibre from outside | `celestia_mon_tensile` | FibreDown's outside branches pending ("Unreachable", "Not registered", "Wrong host"), TensileUnreadable ("Check stopped") | FibreDown fired: "Unreachable", "Wrong host" or "Not registered" | minutes in which a check under 15 minutes old reached the registered endpoint |
| one line per server | always | MonitorCannotReach for the server ("Not reached"), ServiceDown in its words ("Not reporting", "No node data", "Node stopped", "Node crashing" and the others), DiskLow ("Disk low"), NodePeersLow's message ("Few peers"), NodeBehind ("Node behind"), RaidDegraded ("RAID degraded"), ClockNotSynced ("No time sync"), another warning that names the server ("Warning"); on the monitor's line also MonitoringBroken ("Rules failing"), NotificationsFailing ("Alerts unsent"), DeadmanFailing ("No heartbeat"), AnnouncementsUnreadable ("Feed stopped"), Alertmanager down ("Alerting down") and no heartbeat while the alert rules ran ("No heartbeat": for the hour after a notification failed) | DiskLow paged ("Disk critical": full or read-only); NodePeersLow paged ("No peers": the node the validator signs through had none); MonitorCannotReach paged, on every line but the monitor's ("Not reached": the monitor reaches no server) | minutes in which all the server's metrics endpoints answered, its disk was not full or read-only and its node was not without peers while the validator signed through it |

Green on Remote signer needs real signatures in the block (the median latency freezes when tmkms stops), and green on Fibre from outside needs a reading under 15 minutes old. While the nodes are stalled, Validator signing turns grey ("Nodes stalled"): ValidatorNotSigning is held back then. In the block in which Prometheus started, no line turns amber for an alert that was only pending: its first evaluations there can leave a short pending with no fault behind it. Every % leaves out the minutes in which Prometheus did not scrape itself throughout, the minute it starts included. Prometheus keeps 30 days (`celestia_mon_prometheus_retention`) or 8 GB; older bars are grey.

### Role band

Which server held each role over the same time, read from the metrics: **Validator signs through** (the node the validator's signatures went through), with Fibre on **Fibre active on** (the host whose Fibre unit systemd reported active), and with Fibre and a remote signer **Fibre signs through** (the node Fibre sends its signing requests to, from its raw-bytes signatures in the last 15 minutes, else the last hour). A tmkms repoint or a Fibre failover shows as the name changing, and each repoint also puts a marker on the band and the Validator charts. Segments are tinted in the server's colour. Amber: nobody held the role, two servers did ("Two signers" while ValidatorSigningTwice is pending, "Two Fibres"), or Fibre signs through another node than the one the validator signs through (after a repoint, a Fibre that still dials the old node fails every upload: point its signer address at the signing node); not while no node signs at all, which is the signer's outage. Red: the page alert for it fired ("Two signers" once ValidatorSigningTwice pages, "Not running" once FibreDown pages). Grey "No data" where monitoring had no data, as on the bars; grey "Out of set" only where the validator was out of the set within the step, never in the first 2 minutes after a start; grey "Nodes stalled" where no node committed a block for 2 minutes; grey "Switching" where two nodes signed within the step, as during a tmkms repoint ("Two nodes" with `celestia_mon_signer_multi_node: true`); grey "None seen, 1 h" on Fibre signs through where Fibre made no signature in the last hour, as on a quiet network. The remote signer's card falls back to the last day in its own Fibre signs through row and reads "None in 24 h" only after a day without one, so on a quiet network the band can be grey while the card still names a node. On long ranges each step shows its worst moment, a Fibre outage included. The band's bars end where History's end; the key line under it gives the range's first and last moment in UTC, the servers' names in their colours (on a wide enough screen) and the states.

### Servers now (five servers or more)

In place of the Servers band, one row per server, in inventory order, even when nothing is read from it: "no data" means the server should report a value and does not, "–" that it does not apply.

- **Server**: the name, in the server's colour (the key to every chart).
- **Role**: what the server does now, read from the metrics: "Signing node", "Backup node", amber "Node, not signing" while no node signs; "Fibre active", grey "Fibre standby"; on a KMS host with `celestia_mon_kms_scrape`, "Remote signer", amber "Signer down" (stopped) or "No signer" (not loaded), ServiceDown's words; "Monitoring" on a monitor with a host of its own. A server with several roles names each. Amber "Not reporting" while its node_exporter does not answer. Where the full words would not fit the table on a 1440-pixel screen, the dashboard uses short ones ("Signing", "Backup", "Not signing", "Fibre").
- **Node**: "in sync" within 5 blocks of the highest node, else the blocks it trails ("12 behind", amber above 20, NodeBehind's level); amber "stalled" or "No node data" (celestia-appd's metrics are gone), plain "syncing" during block sync.
- **Peers**: connected peers. Amber "Few peers" while the node has fewer than 2 (`peers_message_below`, NodePeersLow pending or firing); red "No peers" once NodePeersLow pages for the node the validator signs through.
- **Signing time** (remote signer): the median of the last 50 signatures on the node that signs now, amber from 10 ms (`signer_median_seconds`, RemoteSignerProblem). Grey "> 10 ms, stale" on a node that tmkms left: it keeps its last median, which RemoteSignerProblem leaves out 5 minutes after the repoint. "Not signing" while the validator is asked to sign and no node signs; "Bad proposals" while RemoteSignerProblem's proposal condition holds: proposal signing failed in the last 6 hours for another reason than a timeout or a lost connection.
- **CPU**, **Memory**, **Network peak**: the share in use, as grey bars; no alert watches them. Network peak is the busiest minute of the last hour against `celestia_mon_link_mbps` or the NIC speed ("speed unknown" when neither is known: set `celestia_mon_link_mbps`).
- **Disk used**: the fullest disk DiskLow watches on the server, the data disks you listed and the Fibre store, as a grey bar. A rule's live condition replaces the number with DiskLow's words: amber "Disk low" below 10% free (`disk_message_free_ratio`; on a Fibre store only while Fibre reports no storage budget, since with a budget its fill is normal), while a Fibre store has less free space than its storage budget still needs, or while a disk is read-only; red "Disk critical" only when DiskLow pages, so a Fibre-only server or a monitor's own host, where DiskLow sends messages, never turns red.
- **Restarts**: automatic restarts of celestia-appd, Fibre and tmkms by systemd in 24 hours; at more than 2 in 30 minutes (`crashloop_restarts`), ServiceDown's amber words for the unit: "Node crashing", "Fibre crash" or "Signer crash".

## All firing alerts

Closed, right under the first screen, one click from the Status cell. Every alert Prometheus has firing now, and those whose problem is true but has not lasted long enough to be sent, each in a plain sentence, with the rule name your notifications carry: **Alert** ("Validator not signing", "Disk low or read-only on fibre-1"); **Rule**, the alert's name as the first line of its notification carries it ("🔴 PAGE · ValidatorNotSigning · val-1"), which opens the alert's entry in the [alert reference](alerts.md) (its meaning and first checks); **Level** ("Urgent", "Urgent, not paged yet", "Warning", "Warning, not sent yet"); and **Active for**, how long since the problem started, including the waiting time before it fired. The heartbeat is left out, and silences do not hide alerts here. With nothing firing it reads "No alerts firing".

## Validator

One strip of six cells in the top strip's form and value size, then the charts behind the Validator and Signing through answers, all one height: two lines of two with a remote signer; with a local key, Missed blocks across the row over Proposals per hour and Block processing time. Everything the validator signs is drawn in the colour of the server whose node it signs through, so after a repoint the colour changes with it; the whole network is drawn in the text colour.

- **Blocks since signature** (ValidatorNotSigning): blocks since the validator's last signature on any node, so the count carries on after a repoint: 0 or 1 while it signs. Amber above 10 blocks (`not_signing_blocks`), where ValidatorNotSigning sends an urgent alert after 2 minutes. The value stops at 10 times that; right after a node start it reads that until the first signature. Red "Not signing" once ValidatorNotSigning pages: the count would only show its cap. While no node makes new blocks, the Status reads "Nodes stalled" and the cell keeps the count.
- **Missed blocks, 1 h** (SignaturesMissed): the share of the last hour's blocks without the validator's signature, as SignaturesMissed computes it (the blocks the node counted as missed in the hour, over the blocks of the hour); amber above 5% (`signatures_missed_ratio`), where SignaturesMissed sends a warning after 10 minutes.
- **Signing time** (remote signer, RemoteSignerProblem): the median of the last 50 signatures on the node the validator signs through, with 2 decimals ("1.90 ms"); amber above 10 ms (`signer_median_seconds`), where RemoteSignerProblem sends a warning after 15 minutes. "No reading" while no node signs, or before a node's 50th signature since it started. With a local key this place shows **Peers**: the peers of the node the validator signs through ("No node signs" while none signs). NodePeersLow sends a warning after 5 minutes below 2 peers (`peers_message_below`) and pages after 1 minute without any: the node then receives no blocks or votes, and the validator misses every block.
- **Proposals signed, 24 h**: with a remote signer, the proposals tmkms signed; with a local key (**Proposals built, 24 h**), the proposals the node built. **Proposals due, 24 h**: the blocks of the last 24 hours times the validator's share of voting power now; proposers take turns by stake, so the two should be close. It reads "Out of set" while the validator is not in the active set, "No new blocks" while the chain stalls and "No node" without a node. **Missed proposals, 24 h**: the validator's turns whose proposal did not reach the nodes in time. The counts cover the last 24 hours, or the time since monitoring started when that is less, carry on across node restarts, and read "No data" when no node answered in the whole 24 hours.
- **Missed blocks** (SignaturesMissed): the share of the last hour's blocks without the validator's signature over time, the value SignaturesMissed reads at each point, with its dashed 5% line; the legend names that level ("<server> missed, 1 h (alert at 5%)"). A miss lifts the line for an hour, so its rising edge marks when. The dashed line in the text colour is the whole network: the share of all voting power missing from recent blocks, averaged over the hour. The validator's line high and the network's low points at this setup; both high, at the network. While no node signs, the share the nodes count is a dotted grey line, kept off the legend and named in the tooltip ("Missed, 1 h, while no node signs"). A red band marks where ValidatorNotSigning paged: no node signed, so the line in the node's colour stops. The axis is linear up to 0.1% and logarithmic above, so the usual 0.1-1% sits mid-chart; it ends at twice the alert level (10%), and a higher share runs along the top. Its labels carry no fixed decimals ("0.5%", "10%"). The value axis draws no grid lines: on a log axis they would stripe the plot at every 2 to 9.
- **Signing time** (remote signer, RemoteSignerProblem): on the node the validator signs through, the median of the last 50 signatures (solid; its legend names the alert level, and the dashed 10 ms line belongs to it alone) and the slowest 1% of vote signatures over 5 minutes (dotted, 1 px, in a darker shade of the node's colour; for context, no alert reads it). As on Missed blocks, the value axis draws no grid lines. The axis is logarithmic, 0.1 to 100 ms, so a slow median stays in sight next to the usual one. Grey bars on a right axis count failed signing requests per time block (`cometbft_privval_signing_failures_total`: timeouts, lost connections, Fibre's raw-bytes signatures and others; every retry counts); none on a healthy setup. A node tmkms left is not drawn. A red band marks where ValidatorNotSigning paged: no node signed, so the lines stop. The remote signer's card shows the slowest 1% of Fibre's signatures.
- **Proposals per hour**: the proposals signed (or built) through each node per hour as bars in the node's colour, missed proposals stacked on top in grey, against the dashed **Expected** line, the number the validator's share of voting power should bring. A signer that signs votes but not proposals leaves the bars short. A bar beside an outage counts only the minutes Prometheus could read its node. Each bar is a whole hour and ends at its time, with Expected over it, so the hour that runs now shows once it ends. A red band marks where ValidatorNotSigning paged: no node signed, proposals included.
- **Block processing time (slowest 1%)**: one line per node: the slowest 1% of checking a proposed block plus the slowest 1% of applying a committed one, over at least 10 minutes. The node the validator signs through is solid; the backup nodes are dashed ("<server> backup"). A node that is too slow votes late, which shows as missed blocks; all nodes slow points at a heavy block, one node at its CPU or disk. The axis is logarithmic, 10 ms to 10 s, so a slow block after a restart stays in view while the usual 40-60 ms lines sit about a quarter up, where a node that slowly gets slower shows; as on Missed blocks, it draws no value grid lines. A red band marks where ValidatorNotSigning paged, as no node signed; a node that runs keeps its line.

## Fibre

Only with `celestia_mon_fibre_enabled: true`. Only the active Fibre sends Fibre metrics, so the panels follow it after a failover, in the colour of the server it runs on. Six facts in the top strip's style and value size (the label over the value), then the Upload readiness line, then four charts in two lines: the two that the Fibre alerts read, then Uploads and Downloads. A red band across the four charts marks where FibreDown paged: no Fibre server ran, so their lines and bars stop. The facts count over the last 24 hours, so a network that sends no blobs for hours leaves them readable, and a quiet network turns nothing amber.

- **Uploads accepted, 24 h**: uploads this Fibre accepted and signed, across Fibre restarts and failovers, from the first upload while monitoring is younger than a day. A client may send an upload again, so it can exceed the blobs sent to the validator. "No Fibre data" while no Fibre metrics arrive.
- With the outside check (`celestia_mon_tensile`), as "215/216" from [Tensile](https://tensile.huginn.tech): **Blobs endorsed, 24 h**, the blobs that settled with the validator's signature, of those sent to it. A blob settles once 2/3 of the voting power has signed, so a healthy validator that answers after that quorum is left out of some; no colour, no alert. **Rows served, 24 h**: of Tensile's reads of the rows the validator signed for, those that got the rows back. From 2 failed reads in 24 hours, the level at which FibreNotServing (rows not served) fires, the text is amber. "No blobs sent" and "No rows read" on a quiet network; "Not checked", in grey, while there is no Tensile reading.
- Without the outside check: **Upload success, 24 h**, the share of upload requests Fibre accepted (failures include clients' invalid payment promises and uploads refused while the budget is full), and **Last accepted upload** ("3 minutes ago"; "None since start" while Fibre reports but has accepted no upload since it started; up to a minute late, as Fibre pushes its metrics that often, so an upload in the last minute reads "a minute ago"). Nothing on your servers tells a quiet network from a Fibre that receives nothing; the outside check does.
- In both: **Upload time, 24 h**, the average accepted upload: checking the payment promise and the rows, writing the shard and signing it through the validator's signer. Fibre's own dashboard splits it by step; the step chart this row once had was empty whenever no blob came. **Storage budget used**: at 100% Fibre refuses uploads (the Fibre tile reads Uploads failing while FibreNotServing holds); it follows the whole network's Fibre data over the 4-hour retention window, so a high share usually means network load. "No limit": unlimited, or the validator was out of the active set when Fibre started; "Not running": no Fibre unit is active. **Failed clean-ups, 24 h**: failed runs of Fibre's removal of old shards; 0 on a healthy server. A failed run leaves old shards on disk, so the store fills.
- The 24-hour counts read each counter once a minute and fill a gap with 0 only while the same Fibre reports its storage budget, so a restart of Fibre or of its collector, after which the counters come back at their running totals, is never counted as growth.
- **Upload readiness** (FibreNotServing, not ready): one line of bars like History's, each block at its worst moment, with the share of the range in which Fibre answered Ready beside it, where History prints its uptimes. The bars show what the running Fibre answered its own health check over the selected time, and start and end where History's do; the share counts only the time Fibre answered at all (Ready or Not ready), and reads "No data" while it answered neither. "Ready" in green: Fibre answered SERVING, so its six checks pass (app node, Fibre module, signer, validator in the active set, provider registration and store; [alerts.md](alerts.md#fibrenotserving) lists them and what Fibre logs when one fails). "Not ready" in amber where Fibre answered NOT_SERVING: a check fails, or Fibre was starting or stopping, which a restart shows for a moment beside its start marker. The message is sent after 3 minutes; the bars are red where the page fired, after 10. "Not reported", grey: the Fibre has no health check (before celestia-app v10.5.0). "Not checked", grey: no answer, as while no Fibre runs or the monitor cannot reach Fibre's port (`sudo celestia-mon-doctor` on the monitor says why). Grey "No data" where monitoring had no data. Every Fibre host is asked, and a stopped standby does not answer, so it adds nothing beside the Fibre that runs.
- **Fibre behind the network** (with the outside check; FibreNotServing, uploads missed): how far Fibre's last accepted upload (or its start, if later) trails the newest blob sent to the validator, in minutes, in the server's colour, with the alert's level as a dashed line at 5 minutes, which the legend names ("<server> behind the network (alert at 5 min)"). It draws the rule's own value: Tensile's record is read a minute late, so Fibre's report of an upload is in first. A blob settles a few seconds after Fibre's upload of it, so a gap up to 1 minute draws as 0: a healthy server and a quiet network draw a line on 0, which also shows that the check is read. A blob Fibre missed rises as a block that stays until Fibre accepts an upload again; the message is sent when the block stays above the line for 5 minutes, so a slow settle, a low block under the line, sends nothing. "Not checked", in grey, while there is no Tensile reading or no Fibre that runs and reports.
- **Uploads failing** (without the outside check; FibreNotServing, uploads failing): the share of upload requests that failed over 5-minute windows, the rule's window, with a dashed line at 100%, which the legend names ("<server> share failing (alert at 100%)"): there no upload was accepted, and after 10 minutes there the message is sent. Clients' invalid payment promises make small rises; a quiet network leaves it empty.
- **Fibre disk and budget** (DiskLow, Fibre store): free space on the store of the Fibre that runs (solid, "<server> free space") and what Fibre may still write under its budget (dashed, "<server> Fibre may still write": the budget minus what it holds). The band between them is the headroom, and it must not close. The axis ends a fifth above the highest line, so the free space does not run along the chart's top edge. A standby's store is left out, since its free space set the axis far above the active store's; its disk is on its server's Disk used chart.
- **Uploads** (FibreNotServing, uploads failing): upload requests per 30-minute block on 24 hours (about 3 hours on 7 days) as stacked bars, on a plain count axis from 0 that reaches at least 3, so a single request is a short bar. Each bar is the block that ends at its time. Accepted in the server's colour, failed in light grey, and refused because the storage budget is full as outlines in the text colour: no alert watches a refusal. Failed uploads and none accepted is what FibreNotServing (uploads failing) watches. A block without requests draws nothing.
- **Downloads**: shard download requests per block, counted the same way: served in the server's colour, not held or failed as grey outlines. Most failed downloads ask for shards Fibre does not hold (pruned after the 4-hour window, or never assigned to it), which is normal; whether Fibre serves the rows the validator signed for is Rows served (with the outside check).

## Servers

Open. One column of charts for each server, in inventory order and in the server's colour, each chart titled with the server's name first ("fibre-server · CPU by service"), so a server's charts sit under one another and each line compares the servers. Two servers take half the width each, three a third, four a quarter; a single server's charts sit three to a line. Where the columns are too narrow for the full words (three servers and more, on a 1440-pixel screen), titles use short ones ("Disk I/O") and legends say "Node" for the consensus node. The parts of a whole are the server's colour and darker shades of it; all in use is a line in the text colour. The lower side of a chart drawn above and below zero is a darker shade of the server's colour. No alert watches CPU, memory or traffic. The disks are in the closed row below.

- **CPU by service**: the share of all the server's cores in use, 5-minute averages, stacked by what uses it: **Consensus node** (celestia-appd's own CPU time), **Monitoring** (Prometheus and Alertmanager, on the monitor host) and **Other**, everything else. On a Fibre host the rest reads **Fibre and other** while the Fibre unit is active there, because Fibre reports no CPU time of its own, and **Other** while it is stopped. The line on top is all in use, drawn in the text colour and named **In use** in the legend where every chart of the line has room for it, else in the tooltip only; the chart's top is all the cores. iowait is not counted as in use; on a VM, steal is.
- **Memory by service**: the same parts in bytes, with **Fibre** (the memory Fibre's Go runtime holds, a little under its real use) on a Fibre host where Fibre runs. The line on top is all in use (installed minus available, so cache that can be freed is left out), drawn in the text colour and named **In use** in the legend as on CPU, and the axis ends a fifth above it; the share of the installed memory is the Memory bar under the server cards. Fibre can use about 27 GiB at its default limits ([connection caps and memory](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/fibre/cmd/README.md#connection-caps-and-memory)). A marker in the text colour shows each time the kernel killed a process for lack of memory (`journalctl -k` names it).
- **Network in and out**: bits per second through the server's network ports, **In** above zero and **Out (below)**. Virtual interfaces, bond and team masters and VLAN sub-interfaces are left out; their member ports count. The Network peak bar under the server cards shows the busiest minute of the last hour against the link speed; Fibre's own traffic is in the Fibre row's Uploads and Downloads.

## Servers: disks, restarts and clocks

Closed. First the same columns as above for the disks, then Restarts and Clock maximum error, each one chart of every server across the full width.

- **Disk used** (DiskLow): how full each data disk you listed ("Data disk /var/lib/celestia") and each Fibre store ("Fibre store /var/lib/fibre") is, as the Disk used bar under the server cards reads it; that bar also shows its alert colour now. The title names the levels its dashed lines draw ("validator-server · Disk used (alert at 90%, 95%)"), or reads "Disk used" alone on every chart of the line where the longest title would not fit. The amber dashed line is at 90% used, DiskLow's 10% free (`disk_message_free_ratio`), where it sends a message after 10 minutes (on a Fibre store only while Fibre reports no storage budget); on servers with celestia-appd or tmkms and a listed data disk the red dashed line is at 95% used, DiskLow's 5% free (`disk_page_free_ratio`), where it pages for a data disk, as it does for a read-only one. A server with no listed disk shows its root filesystem, which no alert watches, under the plain title. Disks fill over days, so the chart is shorter than the others.
- **Disk latency**: how long one write (above zero) and one read (**Read (below)**) took on average over the server's physical disks, on an axis that shows at least 10 ms each way; above about 10 ms on NVMe the disk is overloaded or the provider's storage is slow. LVM, RAID, ZFS volumes and CD drives are left out; their physical disks count. Where the monitor shares a disk with the validator or Fibre, measure it around Prometheus's compactions on the first deploy ([quickstart step 9](quickstart.md#9-run-doctor)).
- **Disk reads and writes** (**Disk I/O** in narrow columns): bytes written (above zero) and read (below) per second.
- **Restarts (alert above 2 in 30 min)** (ServiceDown, crash loop): automatic restarts by systemd of each service ServiceDown watches, one bar series per server and service ("validator-server · Consensus node", "fibre-server · Fibre", "kms-server · Remote signer"), in the server's colour. Each bar is the most restarts within any 30 minutes that end in its time block (30 minutes on the default 24 hours, longer on long ranges): the value the crash-loop rule compares, so a bar above the dashed line (more than 2, `crashloop_restarts`) means ServiceDown reported a crash loop. A single restart lifts the bars of the 30 minutes after it, so at most two bars show it. Bars of two services at one time overlap; the tooltip lists each. With no automatic restart in the selected time the chart reads "No automatic restarts in this time". A start by hand is not counted here; it shows as a grey marker on its server's charts.
- **Clock maximum error (alert at 16 s)** (ClockNotSynced): how far each server's clock may be off at most, by its time sync's own account (the kernel's maximum error), one line per server on a linear axis from 0 to 20 s. chrony sets it at each clock update and systemd-timesyncd at each correction (to 0), and the kernel adds 0.5 ms a second in between, so working time sync draws a low ripple along the floor, about a second or less. At the dashed line, 16 s, the kernel counts the clock as not synchronised, and after an hour there ClockNotSynced sends a message. When time sync stops, the line climbs straight towards the dashed line, which it reaches about 9 hours after the last update, and then lies on it, as the kernel caps the value at 16 s. The chart cannot show a clock synchronised to a wrong source: `chronyc tracking`, `timedatectl timesync-status` and `celestia-mon-doctor` check 9 show the offset the daemon measures.

## Network upgrade

Closed; with `celestia_mon_signal`. One strip of six cells in the top strip's form and value size. **App version**: the version the chain runs now. **Next version**: the version validators signal for, the app version plus one. **Signalled version**: the version the validator signalled for the next upgrade. "None": no signal for the next version yet, also when its last signal was for an earlier round. **Voting power signalled**: the share of all voting power that signalled the next version. **Needed to schedule**: the share that must signal before anyone can schedule the upgrade, 5/6 rounded up to whole voting power. **Upgrade**: "None pending" between upgrades; once one is scheduled, the cell is titled with its height ("Upgrade at 1234567") and shows the time until it at the block time of the last 1000 blocks, amber under 24 hours. Each cell reads the last value of the past 7 days, as the upgrade alerts do, so a short collector outage keeps the last reading; with none, it reads "Not checked" in grey.

## Markers and links

Charts carry faint grey markers behind the data, hidden from the dashboard's controls: "<unit> started on <server>" each time systemd starts a unit, celestia-appd's and tmkms's on the Validator charts, Fibre's on the Fibre charts (on Upload readiness too); "Validator signs through <server>" at each repoint (on the role band too); with `celestia_mon_signal`, "Network upgrade: new app version" on the role band and every chart; with `celestia_mon_announcements`, "Celestia announcement" on the role band, the Validator and the Fibre charts (its text is in your alert channel). Each chart's (i) names the grey lines it can show. "Out of memory on <server>" shows on that server's Memory by service in the text colour. A column chart of the Servers rows shows the starts of its own server only. Two red regions shade the time an outage paged: "Validator not signing" (ValidatorNotSigning) on the Validator charts and, with Fibre on, "No Fibre server running" (FibreDown) on the Fibre charts. Markers can be missed on ranges longer than about a week, where Grafana takes coarser steps.

Each panel's (i) ends with links to the alerts it shows in the [alert reference](alerts.md) and to related pages. The dashboard's links open the alert reference, [Node Exporter Full](https://grafana.com/grafana/dashboards/1860-node-exporter-full/) for everything else about a server, and with Fibre on the official [Fibre dashboard](https://github.com/celestiaorg/celestia-app/blob/v10.4.0/observability/docker/grafana/dashboards/fibre.json) and [Tensile](https://tensile.huginn.tech).
